This dictionary matches `schema.sql` and the objects installed by `logic_layer.sql` or migration 001 in `migrations.sql`. All project objects use the `restaurant` schema. The final design contains eight core tables and one audit table.

PK = primary key. FK = foreign key. Nullable indicates whether SQL NULL is permitted. "None" means a value must be supplied unless an identity generates it. Nullable columns without an explicit default receive NULL when omitted. Identity values come from a PostgreSQL sequence; gaps are normal. `NUMERIC(10,2)` stores exact decimal values with ten total digits and two decimal places. The sample monetary values represent US dollars; there is no currency-code column.

## Foreign-key actions and business rules

All seven foreign keys use `ON DELETE RESTRICT ON UPDATE CASCADE`. Required child foreign keys mean every child has one referenced parent. A parent may have zero or many children.

| Child column | Parent key | Reason to restrict deletion |
|---|---|---|
| menu_item.category_id | menu_category.category_id | Keep categories while menu items refer to them. |
| restaurant_order.customer_id | customer.customer_id | Preserve customer attribution for order history. |
| restaurant_order.employee_id | employee.employee_id | Preserve the employee responsible for an order. |
| restaurant_order.table_id | restaurant_table.table_id | Preserve the seating reference in order history. |
| order_item.order_id | restaurant_order.order_id | Prevent an order deletion while its lines exist. |
| order_item.menu_item_id | menu_item.menu_item_id | Preserve menu references in historical orders; mark discontinued items unavailable. |
| payment.order_id | restaurant_order.order_id | Preserve order references for payments. |

`ON UPDATE CASCADE` propagates a corrected parent key to its child references. Identity IDs should normally remain stable. The audit table intentionally has no FK so its stored identity and name can remain as historical snapshots.

## Derived views and their output columns

Views are saved queries, not additional stored tables. The calculated totals below do not add denormalized columns to the base tables.

### restaurant.v_order_details

| Output column | Data type | Meaning |
|---|---|---|
| order_id | INTEGER | Order identifier. |
| customer_name | TEXT | Customer first and last names joined with a space. |
| item_name | VARCHAR(100) | Current menu-item name. |
| quantity | INTEGER | Units on the order line. |
| unit_price | NUMERIC(10,2) | Historical price on the order line. |
| line_total | NUMERIC | quantity multiplied by unit_price. |
| order_item_id | INTEGER | Source order-line identifier. |

This view uses inner joins and returns one row per matching order line. Orders without lines are absent.

### restaurant.v_order_payment_summary

| Output column | Data type | Meaning |
|---|---|---|
| order_id | INTEGER | Order identifier. |
| order_status | VARCHAR(30) | Recorded order status. |
| order_total | NUMERIC | Sum of line totals; zero when no lines exist. |
| amount_paid | NUMERIC | Sum of Completed payments; zero when none exist. |
| balance_due | NUMERIC | order_total minus amount_paid. |

The view returns every order and aggregates order lines and payments separately before joining them. It does not implement refund accounting or prevent overpayment. An overpayment can produce a negative balance.

## Logic and security notes

- `calculate_order_total(INTEGER)` returns NUMERIC, raises an error for an unknown order, and returns zero for an existing order with no lines.
- `trg_menu_price_audit` runs after a menu price changes and inserts the old/new values into the audit table. Audit inserts belong to the same transaction as the price update.
- The viewer role reads menu items and categories. Staff reads menu items and can update only `availability_status`.
- The order SELECT policy maps `restaurant_customer_a` to customer 1 and `restaurant_customer_b` to customer 2. This is a database-role laboratory, not Supabase Auth integration.
- Customer roles receive no grants on the owner-executed views. Owner, superuser, and BYPASSRLS behavior must be considered when testing RLS.
- Primary keys and the unique table-number constraint create indexes automatically. No additional secondary index was retained after the measured trial.

## Rules that are not fully enforced by the current schema

- A confirmed order should contain at least one line. Foreign keys alone do not enforce that minimum. The transaction demonstration inserts the header and its lines together, but it does not prevent all other direct writes from creating an empty order.
- Employee job roles, order statuses, table status, and item availability do not automatically synchronize or enforce a complete business workflow.
- Email and phone values are not unique and do not have format checks.
- Payment amounts are nonnegative but may exceed an order balance. Refund accounting requires additional business rules.
- Taxes, tips, discounts, ingredients, recipe costs, inventory purchasing, and payroll are outside the implemented columns.
